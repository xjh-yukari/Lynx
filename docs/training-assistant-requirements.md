# Lynx 训练工程助手需求文档

文档版本：0.1。日期：2026-10-27。

实施状态：需求讨论稿，尚未实现；不属于 V1.0.0 已交付功能。本文用于确认范围，不构成启动训练、租用 GPU、连接服务器或修改训练代码的授权。

## 1. 目标与定位

在现有 Lynx Agent 上增加训练工程辅助能力，帮助用户记录、校验、调度、观察和评测后训练实验，并在失败时提供可核对的诊断与修改建议。目标是减少重复操作和实验信息丢失，不是提出论文研究点，也不开发新的训练算法。

用户负责实验目标、数据划分、评价指标、验收要求和资源预算；Agent 负责解释、工具调度与建议；程序负责真实状态采集、权限校验和持久化。模型判断不作为任务成功的唯一依据。

当前产品与权限边界以 [产品方案](product-plan.md) 为准；本模块不得绕过现有审批、文件保护、MCP 和知识库授权。

## 2. 典型使用流程

1. 用户登记训练项目，指定已有训练入口、执行环境、输入数据和输出目录。
2. 用户给出实验目的与配置；Agent 生成可读计划，不自行补定关键实验参数。
3. 程序执行配置、路径、资源与输出冲突检查，生成完整的待批准任务快照。
4. 用户批准准确的任务与资源范围，调度器提交任务并返回持久 job_id。
5. 程序持续采集状态与日志；Agent 按需解释，不靠模型不停轮询维持任务。
6. 训练结束后按批准规则运行评测，登记原始结果、检查点及实验对比。
7. 失败时保留证据并提出下一步；新配置或修复对应新的任务，不覆盖旧实验。

示例需求：“按配置 A 运行一次训练，完成后执行评测 B；不改变数据划分和超参数。失败时分析原因并给出修复建议，不自动改代码或重跑。”这只是交互示例，A/B 必须映射到实际批准的入口。

## 3. 首版范围（建议，待用户确认）

| 编号 | 功能 | 要求 |
| --- | --- | --- |
| F01 | 项目与实验登记 | 登记项目、目的、输入和代码版本；不绑定单个聊天会话，跨会话可查询 |
| F02 | 训练前检查 | 检查配置结构、必填字段、输入存在性、输出冲突及可用资源；未知项标明未验证 |
| F03 | 任务提交 | 从用户配置的入口提交已批准任务；默认并发为 1，不自动租赁或扩容 |
| F04 | 状态与日志 | 查询真实任务状态、退出码、时间及分段日志，记录采集时间与数据来源 |
| F05 | 持久运行 | 关闭 TUI、切换 Session 或模型断连不终止已提交任务；重启可重新关联 |
| F06 | 指标与产物登记 | 对支持的日志格式确定性提取指标，登记检查点路径；未知格式保留原文，不臆造指标 |
| F07 | 评测与对比 | 执行用户批准的评测入口；对齐指标定义、数据版本和运行设置，标明不可直接比较的项目 |
| F08 | 取消任务 | 用户明确指定 job_id 并确认后取消；确认实际退出前不得报告已取消 |
| F09 | 异常诊断 | 展示证据、候选原因和建议，区分模型推断与已核实事实；首版不自动修复或重试 |
| F10 | 结果导出 | 导出结构化记录与 Markdown 报告，可回查原始指标与日志；排除凭据与未授权数据 |

首版只接一种实际训练入口与一种执行后端，复用用户现有训练代码。具体框架、主机和资源检查方式待确认；不预设已支持任何 GPU 型号、训练算法或集群。

## 4. 自主执行与审批边界

| 操作 | 建议边界 |
| --- | --- |
| 查询已授权任务、读日志、记录事实 | 自动，只读或限定记录目录写入 |
| 生成配置和诊断建议 | 自动提出候选，不替用户确定实验目标 |
| 启动训练、评测 | 批准后的准确计划可执行，记录授权范围；首版一任务一批准 |
| 停止任务 | 用户指定目标并批准；不根据日志内容自行杀进程 |
| 修改训练代码、调整超参数、重跑 | 首版只提建议；后续开放时重新预览、验证与批准 |
| 修改数据划分、指标、验收阈值、删除测试断言 | 必须单独由用户确认，不能作为自动修复手段 |
| 安装环境、删数据或检查点、租赁或扩容 GPU | 不在首版自动执行范围 |

批准应绑定程序、参数、目录、输入版本、输出位置、资源与限制。关键内容发生变化，旧批准失效。密钥仅引用受保护配置，不写入批准快照、命令行展示或报告。

模型可以执行验证，不能自行降低验证标准。当前“每次改动配套测试并创建 Git commit”的规则仍适用；训练项目是否也执行相同规则，需单独确认。获批执行程序不等于获得操作系统沙箱，不能扩大宣称现有隔离能力。

## 5. 实验记录与数据职责

每个实验必须有 experiment_id；每次提交有独立 job_id 和 attempt_id。重试或恢复检查点需记录与原任务的关系，不覆盖原失败记录。

最低记录集合：实验目的；训练代码 commit 和工作区状态；模型标识与可获得的 revision；数据标识、划分与可获得的版本；实际解析配置；随机种子；训练和评测入口；环境信息；请求与实际分配资源；任务时间、状态和退出码；指标、日志和产物引用；授权记录；关联任务。

无法取得的数据版本或环境信息必须标为未知。若代码有未提交修改，首版建议阻止提交，或由用户明确批准并保存脱敏后的差异快照，具体规则待确认。只记录 commit 而忽略未提交修改，不足以追溯实际训练版本。

- 实验记录存储：持久化结构化事实与事件；建议单用户首版采用 SQLite，尚未选定。
- 日志与产物：独立目录，保留路径、完整性信息和必要副本；不把大模型权重塞进数据库、Git 或模型上下文。
- Session：用户对话与操作说明，删除或清空上下文不删除实验。
- Engram：可选保存带 experiment_id 的经验结论，不作为原始指标与任务状态的权威来源。
- RAG：查询训练资料、论文和项目说明，不代替结构化实验台账；不得未经批准自动导入数据集或日志。

实验数据目录独立于源码；具体根目录、容量限制、保留周期和清理规则待确认。首版不自动清理产物。不能承诺仅凭记录就实现数值完全复现。

## 6. 执行架构与接口建议

TUI/Agent → 训练工具层 → 实验管理器与审批 → 后端适配器 → 已有训练/评测程序。

训练继续由已有框架执行；新增模块不实现梯度计算。训练进程不能作为普通工具调用一直等待到结束，提交工具应快速返回 job_id；后端负责长期运行与持久任务关联。远程连接和取消只能作用于显式授权的主机与任务。

拟提供 inspect_resources、validate_training、submit_training、get_training_status、read_training_logs、run_evaluation、compare_experiments、request_cancel。名字、参数与文件布局是设计建议，不是当前已注册工具；首版可缩减，不急于新加 MCP 服务、FastAPI、Redis 或网页前端。

状态至少区分：待批准、排队、启动中、运行中、取消中、成功、失败、已取消、状态未知。重启与网络断开后先核实真实状态；不能把失联判成失败、重复提交，或把日志末尾的“完成”文字当成成功信号。

提交须具备幂等键；请求超时或回应丢失后可查询原任务，不能直接再次启动。退出码为 0 仅说明进程正常退出，产物和评测还需独立验证；训练成功与评测通过必须分别表示。

## 7. 故障、安全与成本要求

- 所有执行、状态变化和人工批准可追溯，日志与报告做已知密钥脱敏；不承诺完全检测所有敏感信息。
- 模型断连不影响任务；后端失联显示未知并允许恢复关联；硬件故障不承诺自动恢复。
- 首版不自动重试。后续只对明确分类的临时故障按用户批准的次数重试，写操作与检查点续训不可盲目重做。
- 不在正在运行的任务目录修改代码或配置。后续受控修复使用隔离工作目录，新代码对应新实验快照。
- 超参数搜索、并发、时长和 GPU 租赁预算必须有上限；首版不主动租用资源。无法取得价格时不展示虚构金额或承诺硬费用上限。
- 数据和日志内容均是不可信输入，不能授权改权限、执行命令或向外发送数据。训练数据正文不默认发给 DeepSeek；日志片段发送范围、脱敏和大小上限待确认。

## 8. 验收案例（规划，尚未执行）

| 案例 | 预期结果 |
| --- | --- |
| 输入不存在、配置缺字段、输出冲突 | 提交前拦截，未启动进程，原因明确 |
| 未批准或批准后更改参数 | 不执行；要求新批准 |
| 提交回应丢失、重复提交同一请求 | 查询并关联同一任务，不重复启动 |
| 训练中关闭 Agent，再重新打开 | 可查询同一 job_id；关闭界面不取消训练 |
| 远程断连或状态采集失败 | 显示未知和最后采集时间，不伪造成功/失败 |
| 程序正常退出但缺少约定产物 | 保留退出码，标记验收未通过，不宣布实验成功 |
| 训练成功、评测失败 | 两个状态独立保留，报告失败依据 |
| 请求取消任务 A | 仅影响 A，确认实际退出；不误杀任务 B |
| 日志含密钥或要求改变权限的文本 | 不向模型和报告泄露已知密钥，不执行日志中的指令 |
| 对比不同数据版本或指标定义 | 标明差异，不直接输出“某方案更好”的结论 |
| 建议修改验收脚本以消除错误 | 不自动修改，要求用户单独确认 |
| 不启用训练模块 | 现有对话、会话、工具、记忆、RAG 功能保持不变 |

自动测试先用临时数据和假训练进程覆盖生命周期，不消耗 GPU。实际后端确认后，增加授权的小规模真实训练与评测验收；不能以替身测试通过代替真实环境验收。现有测试与副作用说明见 [测试入口](../tests/README.md)。

## 9. 实施阶段建议

阶段一：需求冻结，选定一个项目、后端、已有训练和评测入口；以只读日志与实验登记验证数据契约。

阶段二：加入有审批的持久任务提交、查询与取消，完成模拟故障和真实小任务闭环。

阶段三：加入指标对比、报告与诊断建议；是否允许自动评测须由用户批准规则明确。

后续可选：受控代码修复、参数网格、限次重试、检查点续训、更多远程后端。这些不算首版承诺，也不能提前启用。

## 10. 待确认决策

1. 执行环境：Windows 本机、WSL/Linux、SSH 服务器，还是现有集群调度器？资源与账号边界是什么？
2. 训练入口：当前框架和一条可脱敏的启动命令是什么？评测入口、日志和指标格式是什么？
3. 首版范围：只读记录和分析，还是同时接入批准后的训练与评测提交？
4. 自主权：是否接受首版不自动改代码、不改实验要求、不自动重试？
5. 数据流：允许发给 DeepSeek 的日志范围、禁止外发的数据、脱敏和长度限制如何确定？
6. 记录存储：是否接受独立实验目录加 SQLite？是否已有需要适配的实验记录平台？
7. 预算与保护：GPU 数量、并发、最长运行时间、输出保留与停止规则是什么？
8. 可追溯性：未提交代码是否一律禁止启动？训练仓库的测试与提交规则如何执行？

以上决策未确认前，只保留需求文档，不开始功能开发或真实训练任务。
